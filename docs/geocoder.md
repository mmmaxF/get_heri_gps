# 陸上・海上の住所判定

陸上は既存の N03 行政区域のポリゴン判定を使用します。住所が見つからない場合、C23 海岸線の最寄り区間に紐づく都道府県・市区町村を返します。例：`兵庫県神戸市沖`。区名は従来どおり `ward` に返し、スーパーには付けません。

## 設定

`reverse_geocoder/.env` に設定します。

```env
OFFSHORE_DISTANCE_M=50000
OFFSHORE_SEARCH_M=60000
GEOCODER_COASTLINE_AUTO_UPDATE=1
GEOCODER_COASTLINE_DB_PATH=/app/data/coastline.sqlite
GEOCODER_COASTLINE_URL_TEMPLATE=https://nlftp.mlit.go.jp/ksj/gml/data/C23/C23-06/C23-06_{code}_GML.zip
```

`DISTANCE` は海岸線からの表示上限（メートル）です。上限を超える場合、従来と同じ `ok: false` / `area not found` を返します。`SEARCH` は検索の余裕で、必ず `DISTANCE` より大きくします。コードの既定値は従来の 3,000 / 4,000 m を維持し、ENV例は 50,000 / 60,000 m としています。

## 海岸線データの準備

起動時、行政区域 DB の更新後に `import_coastlines.py` を実行します。N03 に収録された海沿いの府県の C23 ZIP を取得し、海岸線を最大500 mの区間に分けます。現在の行政境界との交点でも分割し、各区間の中央から最寄りの現在の行政区域に県・市を紐づけます。2006年の行政コードは同距離の候補の選択にだけ使います。行政区域との距離が2 kmを超える区間は紐づけず、件数をログとキャッシュの `metadata.unmatched_count` に記録します。

海岸線には行政区境や湖岸を追加しません。C23 の線だけを利用します。データの年代差や埋め立てにより、現在の海岸とのずれはあり得ます。また、陸上で住所が見つからなかった地点に対して検索するため、未収録の陸地や湖の水面を海と区別する機能はありません。陸上を含む対象地域の N03 を収録してください。

キャッシュは別ファイルに作成してから置き換えます。行政区域 DB または取得先が変わると再構築します。取得済み ZIP は `data/source` に保存されます。通常は海岸線の準備をやり直す必要はありません。

```bash
docker compose exec -T reverse-geocoder python /app/import_coastlines.py --force
```

`--force` は ZIP の再取得も行います。再作成後、コンテナの再起動でメモリ上のインデックスに反映します。取得に失敗した場合は既存キャッシュで起動します。キャッシュがない場合、海上は住所なしを返し、陸上の判定は継続します。

現在の N03 の取得先は [2026年版の全国データ](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N03-2026.html) です。全国47都道府県の行政区域と、海沿いの39都道府県の海岸線を対象にします。

```env
GEOCODER_DATA_URL=https://nlftp.mlit.go.jp/ksj/gml/data/N03/N03-2026/N03-20260101_GML.zip
```

全国版ZIPは約766 MBで、初回の海岸線準備も近畿版より時間とメモリが必要です。行政区域の更新時に海岸線の紐づけも再計算します。県・市の紐づけには準備済みのポリゴンと短い行政境界のインデックスを使用し、長い行政境界の全点を毎回比較する処理を避けています。

## データの利用条件

既定の取得先は国土交通省の [C23 海岸線データ（2006年版）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-C23.html) です。同ページの使用許諾条件は **非商用** です。商用の空撮・放送に使用する場合、この取得先のデータをそのまま採用せず、利用可能な C23 形式の海岸線データを用意して取得先を変更してください。カスタム ZIP は JGD2000、Shift-JIS の C23 polyline shapefile（`C23_001` 属性付き）を想定しています。

## 判定の計算

起動時に海岸線を8,192行ずつ小分けに読み込み、Shapely `STRtree` を作ります。県・市の文字列は区間ごとに複製せず共有します。判定時は緯度経度上の最寄り区間を仮候補として一つ取得し、その区間までの距離をメートルで計算します。この距離は真の最寄り距離の上限となるため、そこまでの検索窓に候補を絞ります。窓には1%と1 mの余裕を持たせ、最小2 km・最大SEARCHとします。必要な場合は窓を拡大します。緯度経度上の距離で県・市を決めることはありません。

候補座標を現在位置を中心とする正距方位図法に変換し、メートル単位で距離を比較します。座標変換と線への距離計算は配列でまとめて処理します。毎回の海岸線のSQL検索やJSON読み込みはありません。完全に同距離なら、県・市・行政コード・区間ID順で決めます。

変更を反映するには `docker compose up -d --build reverse-geocoder` を実行します。初回の海岸線準備には時間がかかるため、準備ログを確認してください。

## テスト

```bash
docker compose run --rm --no-deps --entrypoint python reverse-geocoder -m unittest -v test_geocoder test_import_coastlines
```

陸上優先、最寄りの県・市、距離上限、検索窓の拡大、高緯度、同距離の選択、市境での分割、キャッシュ更新と更新失敗時の保持を確認します。

## 実データでの処理時間（2026-09-17）

Intel Xeon W-2102 / Python 3.12 の独立コンテナで、近畿の行政区域7,490件と海岸線287,142区間を使用しました。距離上限50 km、検索範囲60 kmで各地点20回計測した中央値です。通信・スーパー出力の時間は含みません。キャッシュの読み込みとインデックス作成は約1.68秒でした。

## 全国版の配置・検証（2026-09-17）

`.env` と `.env.example` に距離上限50,000 m・検索範囲60,000 mを設定し、取得先を全国版に変更しました。行政区域DBは47都道府県・125,130件、海岸線キャッシュは39都道府県・5,432,584区間です。両DBの整合性チェックは成功しました。旧近畿DBは `data/admin_area.kinki.backup.sqlite` にバックアップしています。

C23のうち現在の行政区域から2 kmを超えて離れている356区間は、誤った県・市を付けないため対象から除きました。データの年代差による位置ずれや、この除外による未収録区間は残ります。

47都道府県それぞれの代表的な陸上地点、海上11地点と距離上限を超える太平洋上の地点を確認しました。徳島沖・東京湾では全国の海岸線全区間との距離比較も行い、選ばれる県・市が一致しました。単体テスト22件も成功しました。
